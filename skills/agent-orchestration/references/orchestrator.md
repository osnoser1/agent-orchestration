# Orchestrator: ladder, own quota, and launch

Reach this file when you open (or are) a coordinating conversation that delegates children, when its own quota runs `low` or out, and when you launch any top-level conversation from a spec. Coordination rubric and ladder adapted from [claude-code-multi-agent-orchestrator](https://github.com/mdharastani-pixel/claude-code-multi-agent-orchestrator); launch spec and pool caps inspired by [shinpr/sub-agents-skills](https://github.com/shinpr/sub-agents-skills) and Kraft.

## Orchestrator ladder (`select --role orchestrator`)

Choose a coordinating conversation's model with `scripts/orch.py select --role orchestrator --coordination <0|1|2> --available <provider:model,...>` and follow its `action:` line; log it with `log --role orchestrator --rubric <rubric>`. Without Python, apply these rules:

- **Tier and stops**: `coordination` maps through `preferences.orchestrator.tiers` (default `0 → T1`, `1 → T2`, `2 → T3`). When every tier-meeting model is exhausted, hold until renewal (exit `4`) instead of staging below tier, recording a provider-scoped `resume` follow-up (`provider:<id>/<group>/<tier>` when every exhausted candidate shares one quota group, else `provider:<id>/<model-id>` of the earliest reset).
- **Filters and effort cap**: apply the worker filters (`references/selection.md`), exclude models marked `coordinator: true` in `catalog.yaml` (adds a second coordinator under yours), and cap efforts at `preferences.orchestrator.max_effort` (default `high`, maximum `high`). The effort cap `high` applies only to the orchestrator role; workers keep the normal effort rules (e.g., an implementer may need `xhigh`).
- **Start rung**: rank remaining candidates with the worker ranking order (quota health, weak score, policy, reset, cost, effort). Start on the ranked first candidate's tier-meeting effort (effort knee applies), or a higher rated `preferences.orchestrator.defaults[<provider>]` up to `max_effort`.
- **Climb (same provider)**: add the start model's strictly higher-scoring rated efforts up to `max_effort`, then each higher-scoring effort (`<= max_effort`) of other same-provider candidates in rank order, keeping at most `max_escalations + 1` rungs (default 3). An explicit `preferences.orchestrator.ladder` list (`[provider:model@effort, ...]`) overrides `auto` after filtering to available, usable rungs and capping to `max_escalations + 1` (falling back to `auto` if none survive); there, the first surviving other-provider entry is the provider-switch rung. Climb only on an escalation trigger: run `scripts/orch.py escalate --role orchestrator` and follow its `action:` line (`references/escalation.md`); the orchestrator itself (or the user/agent who launched it) switches the conversation's model in place, verifies, and logs it (**Orchestrator's own quota**, step 3).
- **Per-phase effort** (opt-in: `preferences.orchestrator.phase_effort: on`; keep the default `off` until the ledger holds about 10 runs per model@effort, `references/improvement.md`): at each phase boundary run `select --role orchestrator --phase plan|review|supervise --current <base rung>` and follow its `action:` line. Plan and brief stay on the base rung (the rung launched or escalated to), review synthesis takes the next higher rated effort (up to `max_effort`), and supervise, wait, and land take the next lower one (never below `low`); model and provider stay the same. Pass the base rung, not the phase-adjusted effort, as `escalate --current`.
- **Provider switch**: among other-provider candidates in rank order, pick the first with a rated effort (`<= max_effort`) scoring above the ladder's top score at its lowest such effort; if none exceeds the top, pick the highest-scoring other-provider rung (`<= max_effort`) and note it is not an escalation. Raising effort within the same provider is cheap; switch providers only at a phase boundary, because a cross-provider in-place switch hands the context over through a lossy summary (`references/harnesses.md`); ask the user before a provider switch.

## Orchestrator's own quota

Keep coordinating on a usable model when the orchestrating conversation's own pool reaches `low` or is exhausted, selecting replacements through the **Orchestrator ladder**:

1. **Low threshold (before a forced stop)**: run `scripts/orch.py select --role orchestrator --coordination <0|1|2> --ref orchestrator-self` (this conversation's `coordination` score from the `references/selection.md` rubric) with the orchestrator's `low` pool omitted from `--available`. Switch now only on a `launch the orchestrator on …` action; on `hold until`, `ask`, `no usable model`, or `no tier match`, keep coordinating on the `low` pool and clear the entry with `scripts/orch.py followups --done orchestrator-self`.
2. **Exhausted (if this conversation can still run commands)**: run `scripts/orch.py exhaust <provider> "<error>" --self --coordination <0|1|2> --available <provider:model,...> --ref orchestrator-self` (add `--model` or `--group` per `references/quota-errors.md`) and follow its `action:` line; clear `orchestrator-self` with `scripts/orch.py followups --done orchestrator-self` after a resume completes. When the harness already halted the turn on quota, switch or hand off on resume (or from a fresh conversation carrying durable state, `references/supervision.md`) using the target from the last `select` or `exhaust --self` `action:` line.
3. **Switch in place or hand off**: when `select`, `exhaust --self`, or `escalate --role orchestrator` names a target:
   - **Harness can switch this conversation**: apply its **Switch model in place** cell (`references/harnesses.md`). On T3 Code, call `t3_thread_configure` omitting `threadId` with the target `modelSelection`, then call it with no arguments to read this thread's effective `modelSelection` (**verified**) and convert it to `provider:model@effort` (`references/harnesses.md`, **Requested vs effective model**, step 1). Log both with `scripts/orch.py log --event select --role orchestrator --surface conversation --complexity <c> --risk <r> --provider <p> --model <m> --effort <e> --rubric <rubric> --requested <target P:M@E> --effective <read P:M@E> --ref <item>`, where `--provider/--model/--effort` are the target. Handle a `warning: effective … differs` line, or a harness that cannot report the effective model, per step 3 of that `references/harnesses.md` section.
   - **Harness cannot switch its own model**: give the user the command from the harness's **Switch model in place** cell when that command can select the target model (e.g. Claude Code `/model` within Anthropic models); otherwise hand off durable state to a new conversation launched from a `role: orchestrator` spec with `scripts/orch.py launch <spec>` (**Launch and header contract**; follow `SKILL.md` Step 7 for `preferences.new_conversations`).
4. **Nothing usable (`hold until <time>`)**: schedule this conversation's resume at `earliest_reset + 2m` per the **Scheduled resume** column (`references/harnesses.md`; or report the reset time when no scheduler exists) and refresh durable state (`references/supervision.md`).

*Done when*: this conversation runs on a usable model with its effective model/effort verified and logged (or is handed off with durable state), keeps coordinating on its `low` pool with `orchestrator-self` cleared when `select` named no `launch the orchestrator on …` target, or has one resume scheduled (or its reset time reported) after `hold until`.

## Spec keys (`<name>.launch.yaml`)

Use a `<name>.launch.yaml` spec (`assets/orchestrator.launch.example.yaml`) whenever you open a new top-level conversation for an **orchestrator**, or for an **implementer** or **reviewer** that runs as its own top-level conversation (`surface: conversation` in `references/harnesses.md`). Store real specs and briefs in `~/.config/agent-orchestration/plans/` (outside git).

| Key | Required | Values and rules |
|---|---|---|
| `version` | optional | `1` (default `1`) |
| `role` | required | `orchestrator`, `implementer`, or `reviewer` |
| `title` | optional | Conversation title (defaults to the spec filename) |
| `repo` | optional | Repository label (`owner/name` or name); its basename is emitted as `--repo <basename>` on the `log:` line |
| `brief` | required | Path relative to the spec file; must exist and be non-empty |
| `rubric` | required | Map with all six keys (`size`, `uncertainty`, `deps`, `consequences`, `verification`, `coordination`) in `0..2` |
| `ladder` | optional | `auto` (default) or `[provider:model@effort, ...]`; for `orchestrator`, overrides `preferences.orchestrator.ladder` (noted and ignored for worker roles) |
| `implementer` | reviewer only | Implementing model (`provider:model` or model id); required when `role: reviewer` |
| `available` | optional | List of `provider:model` pairs from discovery; `--available` on the CLI overrides it |
| `workspace` | optional | `{strategy: worktree\|root\|existing_worktree, base: <ref>, branch: <name>, children: shared\|worktree, worktree_path: <dir>}`; `base` required for `worktree` (optional `branch` sets `workspaceStrategy.branch`), `worktree_path` for `existing_worktree` |
| `caps` | optional | `{max_escalations: 0..3, max_children_per_pool: N, budget: {<provider>: N}}`; non-negative ints; `max_escalations` overrides `preferences.orchestrator.max_escalations` for `orchestrator` |

## Launch and header contract

1. **Resolve and write payload**: run `python3 scripts/orch.py launch <spec> [--available <provider:model,...>] [--out <file>]` and follow its `action:` line. Unless `--no-probe` is passed (or no `assets.yaml` exists), `orch.py launch` refreshes quota first (`orch.py probe`), classifies the rubric, resolves rung 1 of the orchestrator ladder (or the worker candidate), writes `<name>.payload.json` next to the spec, and prints a ready-to-run `log: orch.py log ...` command (with `--surface conversation`) before `action:` (add back any flags a `note:` says it dropped). Any non-dispatch outcome (hold, stage, gated, ask, or no tier match) exits `3` and points to `orch.py select`. On exit `3` or any error it deletes a stale payload from an earlier run.
2. **Dispatch on the active harness**: the JSON payload (`title`, `message`, `modelSelection` with the discovery harness model id and provider effort option key — `claudeAgent* → effort`, `codex* → reasoningEffort` + `serviceTier: default`, `antigravity → thought_level`, or `effort_key` on the provider in `assets.yaml` — `workspaceStrategy`, `clientRequestId`) targets T3 Code `t3_thread_launch`. On other harnesses, pass the printed `requested:` model/effort and the payload's `message` (header + brief) to the harness's **New conversation** command in `references/harnesses.md`.
3. **Phase-boundary header**: `orch.py launch` prepends a plain-text role header to the brief (`ORCHESTRATOR`, `IMPLEMENTER`, or `REVIEWER`: model and rung, ladder, provider switch, escalation triggers and cap, caps, workspace, rubric, and the launcher's verify duty; worker roles omit ladder, provider-switch, and escalate lines, and degraded reviewers add a `reviewer degraded:` line; read it in the payload's `message`). The launched orchestrator repeats this block, updated with the active rung and remaining escalations/budget, at every phase boundary.
4. **Re-launch after quota renewal**: rerun `python3 scripts/orch.py launch <spec>` on the same spec file when a pool renews to re-probe quota and regenerate the payload. `clientRequestId` ends with `-<YYYYmmddHHMM>` (UTC, from `--now` when given), so a re-launch in a later UTC minute opens a new thread, while a lost-reply retry that resends the same payload file reuses the same id.

*Done when*: `orch.py launch` exits `0`, writes `<name>.payload.json` with the role header prepended to the brief, and the new conversation is launched (or handed to `orch.py select` on exit `3`).
