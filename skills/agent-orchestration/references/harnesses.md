# Harnesses

Choose only models returned by the active harness's discovery step. If a harness cannot pick a model per subagent, run with its default and report that.

## Delegation surface

- **Default (`subagent`)**: delegate as a child task in the current project/checkout so results return to the orchestrator.
- **New top-level conversation (`conversation`)**: open a separate top-level conversation when the work belongs to a different project/repo than the current one, the user should follow or steer it directly, it is long-lived with its own PR lifecycle, or it would bloat the orchestrator's context. Apply the same brief template and model selection, and link the report back to the originating conversation.
- **Authorization**: governed by `preferences.new_conversations: ask|allow` in `assets.yaml` (default `ask`: ask once per `SKILL.md` Step 7, then proceed) and any `Conversations:` line in the target repo's `## Orchestration` (`references/repo-policy.md`). Switching an existing child's model in place, scheduling a resume, and running recurring supervision checks over non-notifying children inside the same conversation stay on the current thread and run under routine orchestration (`SKILL.md` Step 7). Active harness rules remain authoritative.

## Quota recovery: switch in place, new child, or scheduled resume

When a running child (implementer or reviewer) hits a quota limit, follow this exact decision order (no overlap):

1. **Record and re-select**: persist the lockout (`scripts/orch.py exhaust` with `--model` or `--group` as the scope rules in `references/quota-errors.md` require), log `--outcome quota` (`scripts/orch.py log`), and run `scripts/orch.py select` (with `--implementer <model-id>` for a reviewer), which applies the quota-pool fallback rule and `preferences.below_tier` (`references/selection.md`).
2. **Candidate exists and harness can switch model in place**: switch the existing child's model so it keeps its full context (see **Switch model in place** below). When `select` prints a `STAGE` plan, switch only a child whose remaining work is Phase 1 preparation; the `stage` phase-boundary switch onto an exhausted target follows `references/selection.md`. After switching, read the child's state (`t3_thread_read` / task status in T3 Code, or the harness's equivalent):
   - If a turn is already running or queued on its own, send nothing (an extra message starts a duplicate turn).
   - If the child is idle, send one short message (passing an idempotency key derived from the child's last observed turn/message ID when supported, `references/supervision.md`): `"continue from where you stopped; re-run any interrupted command in the foreground"`.
   Log the continuation selection (`scripts/orch.py log --event select`).
3. **Candidate exists and harness cannot switch model in place**: start a new child on the same `surface` with the original brief plus partial results (branch/commit/worktree and last completed step) and log the continuation selection.
4. **No usable candidate (`orch.py select` exits `4`), a `STAGE` plan for a child already past preparation, or a `stage` Phase 2 double check**: keep emergency and pay-per-use models excluded; they run only after the one approval in `SKILL.md` Step 7. Record a pending resume in `assets.yaml` (`orch.py select ... --ref <ref>` or `orch.py followups --add --kind resume --ref <ref> --needs <tier> --after <earliest_reset + 2m>`; deduplicated per `ref` so later conversations skip duplicate scheduling). If the harness supports delayed scheduling (see **Scheduled resume** below), schedule one resume at `earliest_reset + 2m` for the same child conversation and inform the user once; at wakeup it re-reads the child, derives the idempotency key from the turn observed then, and sends only while the child is idle. Without a scheduler, report the earliest reset time to the user. Clear the follow-up with `orch.py followups --done <ref>` when the child resumes.
5. **Gate stop (`orch.py select` exits `3`)**: on `ASK`, ask the user once (`SKILL.md` Step 7) and apply the answer; on `DEFER`, wait like step 4 using the printed reset; on a pre-flight threshold block (`--fail-on-low`), rerun `select` without it or wait like step 4.

*Done when*: the lockout and outcome are logged, and the child is running on a usable model, waiting on one recorded `resume` follow-up with its wakeup scheduled (or its reset time reported), or waiting on the user's answer to one question.
